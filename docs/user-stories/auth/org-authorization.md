# 第三方应用 用户故事（org-authorization）

> 角色定义见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)

语境说明：本组故事中「组织」是 Herald 为下游应用托管的实例级成员分组（通用概念，下游应用内的 workspace、团队等均映射为组织）；成员管理动作由应用后端持 client 凭证发起，应用终端用户经由应用提供的界面间接触发。

## 用户故事

### 故事 1：创建组织并关联应用侧 workspace [US-OA-001]

**优先级**: P0

**【用户故事】**
**作为**：第三方应用（详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)）
**我希望**：在应用内创建 workspace 时，由应用后端在 Herald 建立对应的组织，并登记应用侧标识与该组织的关联
**从而**：workspace 的成员与角色由 Herald 统一托管，应用不必自建成员体系

**【验收标准】**

**场景 1：创建成功**
```gherkin
Given 应用已在 Herald 注册为 Client App，且应用后端持有有效凭证
When 应用后端为应用内新建的 workspace 创建组织，并登记该 workspace 的应用侧标识
Then 创建成功，组织归属于该应用所在的 realm 与 Client App，且与应用侧 workspace 建立一一关联
```

**场景 2：同一应用侧标识重复创建**
```gherkin
Given 某应用侧标识已关联一个既有组织
When 应用后端再次以同一应用侧标识创建组织
Then 系统不产生第二个组织，并返回指向既有组织的明确结果
```

### 故事 2：添加成员并赋予组织角色 [US-OA-002]

**优先级**: P0

**【用户故事】**
**作为**：第三方应用
**我希望**：由应用后端把应用内的用户添加为组织成员，并指定其组织角色（如管理员、可编辑、普通成员）
**从而**：应用内 workspace 的协作者角色由 Herald 记录并在判定时生效

**【验收标准】**

**场景 1：添加成功**
```gherkin
Given 组织已存在，且调用方具备该组织的成员管理能力
When 应用后端把同 realm 内的某个账号添加为成员，并指定组织角色
Then 成员关系与角色立即生效，可被组织判定查询到
```

**场景 2：重复添加幂等**
```gherkin
Given 某账号已是该组织成员
When 应用后端再次添加该账号并指定角色
Then 不产生重复成员关系；指定角色与原角色一致时无变化，不一致时更新为新角色
```

**场景 3：跨 realm 账号被拒绝**
```gherkin
Given 目标账号不属于组织所在的 realm
When 应用后端尝试将其添加为成员
Then 操作被拒绝，并提示账号范围不符
```

**场景 4：调用方无管理能力**
```gherkin
Given 调用方不具备该组织的成员管理能力
When 应用后端尝试添加成员
Then 操作被拒绝，成员关系不发生变化
```

### 故事 3：查询用户在组织内的角色与能力判定 [US-OA-003]

**优先级**: P0

**【用户故事】**
**作为**：第三方应用
**我希望**：在用户访问应用内 workspace 时，向 Herald 查询该用户在对应组织的角色，以及按角色解析出的能力判定
**从而**：应用可以按 Herald 的判定对 workspace 操作做门控（管理员/可编辑/仅查看等）

**【验收标准】**

**场景 1：成员判定**
```gherkin
Given 某用户是组织的 admin 角色成员
When 应用后端查询该用户在此组织的角色与能力判定
Then 返回其组织角色，以及该角色按能力词表解析后的判定结果
```

**场景 2：非成员判定**
```gherkin
Given 某用户不是该组织的成员
When 应用后端查询该用户在此组织的角色与能力判定
Then 返回明确的非成员结果，应用可自行决定按拒绝或只读处理
```

**场景 3：移除后近即时生效**
```gherkin
Given 某成员刚被移出组织
When 应用后端随即查询该用户在此组织的判定
Then 返回非成员结果，不存在可感知的延迟窗口
```

### 故事 4：移除成员与变更角色 [US-OA-004]

**优先级**: P0

**【用户故事】**
**作为**：第三方应用
**我希望**：由应用后端移除组织成员或变更其组织角色
**从而**：应用内 workspace 的协作权限可以被收回或调整，且立即生效

**【验收标准】**

**场景 1：移除生效**
```gherkin
Given 组织内存在一名普通成员，调用方具备该组织的成员管理能力
When 应用后端移除该成员
Then 该用户的组织判定立即变为非成员；其在应用内的既有登录态如何处理由应用自行决定
```

**场景 2：最后一名管理员保护**
```gherkin
Given 组织内只剩一名管理员角色的成员
When 应用后端尝试移除该成员或将其降级为非管理员角色
Then 操作被拒绝，并提示需先转移管理权
```

**场景 3：owner 保护**
```gherkin
Given 某成员是组织创建时登记的 owner
When 应用后端尝试移除该成员或降低其角色
Then 操作被拒绝
```

### 故事 5：workspace 管理员协作（提升成员为管理员） [US-OA-005]

**优先级**: P1

**【用户故事】**
**作为**：应用终端用户（Regular User，详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)，此处为持有组织管理员角色的应用用户）
**我希望**：在应用提供的 workspace 管理界面里，把另一位成员提升为管理员
**从而**：workspace 可以多人协作管理，而不必都由应用后端代为操作

**【验收标准】**

**场景 1：提升成功**
```gherkin
Given 操作者是该组织 admin 或 owner 角色成员，且应用管理界面提供了提升入口
When 操作者选择某普通成员并确认提升为管理员（应用后端据此以其名义调用 Herald 的角色变更能力）
Then 该成员随后的组织判定反映管理员角色
```

**场景 2：非管理员操作被拒**
```gherkin
Given 操作者本人不是该组织的管理员角色成员
When 应用以其名义发起提升请求
Then Herald 拒绝该变更，应用界面提示无权限
```

### 故事 6：平台身份不穿透组织判定 [US-OA-006]

**优先级**: P0

**【用户故事】**
**作为**：第三方应用
**我希望**：Herald 的组织判定只依据组织内角色，任何平台侧管理身份都不参与
**从而**：Herald 管理员或 realm 管理员不会自动获得应用内 workspace 的权限，组织间也互不渗透

**【验收标准】**

**场景 1：平台身份无组织权限**
```gherkin
Given 某主体仅持有 Herald 平台管理身份（如 realm 管理员），不是某组织的成员
When 应用后端查询该主体在此组织的判定
Then 返回非成员结果，平台身份不产生任何组织内权限
```

**场景 2：组织间隔离**
```gherkin
Given 某用户是组织 A 的管理员，但不是组织 B 的成员
When 应用后端查询该用户在组织 B 的判定
Then 返回非成员结果
```

### 故事 7：我的组织列表 [US-OA-007]

**优先级**: P2

**【用户故事】**
**作为**：应用终端用户（Regular User，详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)）
**我希望**：应用能向 Herald 查询我加入的全部组织及各自角色
**从而**：应用可以渲染我的 workspace 切换列表并标注我的身份

**【验收标准】**

**场景 1：列表正确**
```gherkin
Given 某用户是同一应用三个组织的成员，角色各不相同
When 应用后端查询该用户的组织列表
Then 返回全部三个组织及各自的角色
```

**场景 2：移除后不再出现**
```gherkin
Given 某用户刚被移出某个组织
When 应用后端查询该用户的组织列表
Then 该组织不再出现在列表中
```
