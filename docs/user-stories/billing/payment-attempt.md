## 用户故事

### 故事 1：创建支付尝试（订阅或积分包） [US-PA-001]

**优先级**: P0

**【用户故事】**
**作为**：Herald 系统（详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)）
**我希望**：为发起式支付平台创建统一的支付尝试
**从而**：统一不同平台的支付流程，并提供一致的支付体验

**【验收标准】**

> 验收标准只描述用户动作与可见结果，不写 API 路径、数据表、字段变更、技术实现步骤。

**场景 1：创建订阅购买的支付尝试**
```gherkin
Given 用户选择了订阅套餐 "pro-monthly"
And 用户选择了支付平台 "Stripe"
And 套餐 "pro-monthly" 已配置 Stripe 支付映射
When 系统创建支付尝试
Then 支付尝试创建成功，包含以下信息：
  | 支付平台     | Stripe                |
  | 购买类型     | 订阅套餐              |
  | 购买对象     | pro-monthly           |
  | 金额         | ¥50.00                |
  | 状态         | 待支付                |
  | 过期时间     | 2 小时后              |
And 系统向 Stripe 发起支付会话创建
And 系统返回 Stripe 支付页面地址给用户
```

**场景 2：创建积分包购买的支付尝试**
```gherkin
Given 用户选择了积分包 "credits-500"
And 用户选择了支付平台 "Stripe"
And 积分包 "credits-500" 已配置 Stripe 支付映射
When 系统创建支付尝试
Then 支付尝试创建成功，包含以下信息：
  | 支付平台     | Stripe                |
  | 购买类型     | 积分包                |
  | 购买对象     | credits-500           |
  | 金额         | ¥50.00                |
  | 状态         | 待支付                |
  | 过期时间     | 2 小时后              |
And 系统向 Stripe 发起支付会话创建
And 系统返回 Stripe 支付页面地址给用户
```

**场景 3：Creem 支付的支付尝试**
```gherkin
Given 用户选择了订阅套餐
And 用户选择了支付平台 "Creem"
When 系统创建支付尝试
Then 支付尝试创建成功
And 系统向 Creem 发起支付订单创建
And 系统返回 Creem 支付页面地址给用户
```

**场景 4：支付尝试唯一性**
```gherkin
Given 用户创建了一个支付尝试
And 支付尝试状态为 "待支付"
When 用户尝试为同一目标创建另一个支付尝试
Then 系统允许创建（不阻止）
And 两个支付尝试互不干扰
And 每个支付尝试有独立的过期时间
```

### 故事 2：查询支付尝试状态 [US-PA-002]

**优先级**: P0

**【用户故事】**
**作为**：Herald 系统
**我希望**：查询支付尝试的状态
**从而**：前端可以轮询展示支付进度，并在支付成功后履约

**【验收标准】**

**场景 1：查询待支付状态的支付尝试**
```gherkin
Given 已存在支付尝试，状态为 "待支付"
When 前端查询支付尝试状态
Then 系统返回支付尝试信息：
  | 状态     | 待支付  |
  | 过期时间 | 2026-04-08 12:00:00 |
And 前端继续轮询
```

**场景 2：查询已成功状态的支付尝试**
```gherkin
Given 已存在支付尝试，状态为 "已成功"
And 已完成履约（发放积分或创建订阅）
When 前端查询支付尝试状态
Then 系统返回支付尝试信息：
  | 状态       | 已成功              |
  | 完成时间   | 2026-04-08 10:05:00 |
And 前端停止轮询
And 前端展示支付成功页面
```

**场景 3：查询失败状态的支付尝试**
```gherkin
Given 已存在支付尝试，状态为 "已失败"
When 前端查询支付尝试状态
Then 系统返回支付尝试信息：
  | 状态           | 已失败  |
  | 平台状态       | 交易失败 |
And 前端停止轮询
And 前端展示支付失败页面
And 提供"重新支付"按钮
```

**场景 4：查询已过期状态的支付尝试**
```gherkin
Given 已存在支付尝试，状态为 "已过期"
And 支付尝试已超过 2 小时未支付
When 前端查询支付尝试状态
Then 系统返回支付尝试信息：
  | 状态     | 已过期  |
And 前端停止轮询
And 前端展示"二维码已过期"提示
And 提供"重新获取二维码"按钮
```

**场景 5：主动查询平台状态（回调未到达时的补偿）**
```gherkin
Given 已存在支付尝试，状态为 "待支付"
And 支付尝试创建已超过 5 分钟
And 未收到支付平台回调通知
When 系统执行补偿查询
Then 系统查询支付平台的实际状态
And 如果平台侧已支付成功，更新本地状态为 "已成功" 并执行履约
And 如果平台侧仍未支付，保持 "待支付" 状态
```

**场景 6：查询需操作状态的支付尝试**
```gherkin
Given 已存在支付尝试，状态为 "需操作"
And 渠道侧要求用户完成额外确认动作（如拉起 App 支付确认）
When 前端查询支付尝试状态
Then 系统返回支付尝试信息：
  | 状态     | 需操作  |
And 前端继续引导用户完成渠道侧操作并轮询
```

### 故事 3：处理支付成功后的履约 [US-PA-003]

**优先级**: P0

**【用户故事】**
**作为**：Herald 系统
**我希望**：根据支付尝试的购买对象执行不同的履约逻辑
**从而**：正确处理订阅购买和积分包购买的履约结果

**【验收标准】**

**场景 1：订阅购买的履约**
```gherkin
Given 支付尝试的目标是订阅套餐 "pro-monthly"
And 支付平台通知支付成功
Or 系统主动查询发现支付成功
When 系统将支付尝试状态更新为 "已成功"
And 系统识别购买类型为 "订阅套餐"
Then 系统执行以下履约逻辑：
  1. 创建或更新订阅记录
  2. 发放会员积分
  3. 记录审计日志
And 履约完成后，用户获得订阅权益和会员积分
```

**场景 2：积分包购买的履约**
```gherkin
Given 支付尝试的目标是积分包 "credits-500"
And 支付平台通知支付成功
Or 系统主动查询发现支付成功
When 系统将支付尝试状态更新为 "已成功"
And 系统识别购买类型为 "积分包"
Then 系统执行以下履约逻辑：
  1. 发放充值积分，不创建订阅
  2. 记录审计日志
And 履约完成后，用户仅获得充值积分
And 系统不创建订阅记录
```

**场景 3：履约幂等性保证**
```gherkin
Given 支付尝试已经履约完成
And 用户已收到积分和订阅
When 系统收到重复的支付成功通知
Or 系统重复查询到支付成功状态
Then 系统识别为重复履约
And 系统不重复发放积分
And 系统不重复创建订阅
```

**场景 4：履约失败处理**
```gherkin
Given 支付尝试支付成功
When 系统执行履约逻辑时发生错误
Then 系统将支付尝试状态标记为 "已成功"（支付已成功）
And 系统记录履约失败日志
And 系统触发告警通知管理员
And 系统提供手动补发积分的功能
```

**场景 5：不同积分类型的发放**
```gherkin
Given 支付尝试的目标是订阅套餐
When 系统执行履约
Then 系统发放会员积分
And 积分有过期时间（随订阅周期）
Given 支付尝试的目标是积分包
When 系统执行履约
Then 系统发放充值积分
And 积分无过期时间（长期有效）
```

### 故事 4：关闭过期的支付尝试 [US-PA-004]

**优先级**: P1

**【用户故事】**
**作为**：Herald 系统
**我希望**：自动关闭过期的支付尝试
**从而**：防止用户扫描过期二维码导致支付异常

**【验收标准】**

**场景 1：自动关闭过期订单**
```gherkin
Given 存在创建超过 2 小时仍未支付的支付尝试
And 支付尝试状态为 "待支付"
When 系统执行定时清理任务
Then 系统通知支付平台关闭该订单
And 系统将支付尝试状态更新为 "已过期"
And 系统记录过期时间
```

**场景 2：关闭订单前确认未支付**
```gherkin
Given 存在即将过期的支付尝试
When 系统准备关闭该支付尝试
Then 系统先查询支付平台侧该订单的实际状态
And 如果平台侧已支付，不执行关单，按支付成功处理并履约
And 如果平台侧未支付，执行关单操作
```

**场景 3：用户重新创建支付尝试**
```gherkin
Given 支付尝试已过期（状态为 "已过期"）
When 用户重新选择订阅套餐并支付
Then 系统创建新的支付尝试
And 新支付尝试与旧支付尝试互不干扰
And 新支付尝试有新的过期时间
```

**场景 4：过期支付尝试的查询**
```gherkin
Given 支付尝试已过期
When 前端查询支付尝试状态
Then 系统返回 "已过期" 状态
And 前端提示用户"二维码已过期，请重新获取"
And 前端提供"重新支付"按钮
```

### 故事 5：用户自助取消支付尝试 [US-PA-005]

**优先级**: P1

**【用户故事】**
**作为**：Regular User（详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)）
**我希望**：在放弃支付时主动取消我的待支付尝试
**从而**：购买页能明确结束支付流程，而不是等待二维码/会话自然过期

**【验收标准】**

**场景 1：取消待支付尝试**
```gherkin
Given 已存在我创建的支付尝试，状态为 "待支付" 或 "需操作"
When 我在购买页选择取消支付
Then 系统将支付尝试状态更新为 "已取消"
And 前端停止轮询并回到购买选项页
```

**场景 2：只能取消自己的尝试**
```gherkin
Given 存在另一用户创建的待支付支付尝试
When 我尝试取消该支付尝试
Then 系统拒绝（我不拥有该尝试）
And 尝试状态保持不变
```

**场景 3：终态不可取消**
```gherkin
Given 支付尝试状态为 "已成功" / "已失败" / "已过期" / "已取消"
When 我尝试取消该支付尝试
Then 系统拒绝非法状态迁移
And 尝试状态保持不变
```
