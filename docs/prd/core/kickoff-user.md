## 2. 范围界定

### 2.1 包含功能

- 管理员查看指定用户当前活跃会话列表（仅限本 Realm），列表展示每个会话的所属 Client App、设备/浏览器（User-Agent）、登录来源 IP、登录时间等可辨识信息
- 管理员撤销指定用户的某个指定活跃会话
- 管理员一键撤销指定用户的全部活跃会话（不改账号状态，用户可重新登录）
- 用户状态变更为 Forbidden 时，系统自动撤销该用户全部活跃会话（即时下线）
- 会话撤销操作与结果记入审计日志

### 2.2 不包含功能 (Out of Scope)

- 会话列表的实时长连接刷新（推送/轮询刷新不在本特性范围，列表为打开时的快照）
- 按 IP、地理位置、设备指纹等维度的会话筛选与风险评分
- 普通用户自助查看/撤销自身全部会话（自助退出仍走既有 logout 能力，不在本特性范围）
- 修改用户状态为 Forbidden 以外的状态变更引发的会话撤销（仅 Forbidden 触发联动）
- 通过 CLI、SDK 或 API Key 以编程方式批量撤销多用户会话
- 会话撤销后向被下线用户的在途请求主动中断（依赖令牌校验自然失败，不做连接级中断）

### 2.3 依赖项

- 浏览器令牌族（Browser Token Family）会话模型与用户维度会话索引已就绪
- 会话元数据（设备/IP）以独立的会话元数据索引形式存放，不写入浏览器令牌族记录本体；具体索引结构归属技术设计
- 用户管理后台与既有 `users.*` 权限模型（见 [权限管理](../auth/permissions.md)、[用户管理](users.md)）
- 审计日志系统与既有 `AuditTargetType::Session` 目标类型
- 用户状态枚举（`WaitVerified / Normal / Forbidden / Deleted`）与用户编辑流程

## 3. 需求概述

### 3.1 功能描述

Herald 的用户管理原先缺少"即时让用户下线"的能力：管理员把用户设为 Forbidden 只能阻止其未来登录，已登录会话最长可存活至 refresh token 的绝对过期；同时没有任何管理员侧入口可以查看或撤销某个用户的活跃会话。这造成"禁用不等于下线"的安全缺口，也无法支撑账号被盗、设备丢失、强制重新认证、离职即时下线等高频安全场景。

本特性为 Realm Admin 提供两个互补能力：（1）在用户管理页面查看并按需撤销指定用户的全部或部分活跃会话；（2）当用户状态被变更为 Forbidden 时，系统自动撤销其全部活跃会话，确保"禁用即下线"。两者共享底层会话撤销能力，但在触发方式（管理员显式操作 vs 状态变更联动）和账号语义（不改状态 vs 禁用）上相互区分。

### 3.2 关键特性

- 管理员可查看指定用户在本 Realm 的全部活跃会话及其可辨识信息
- 管理员可选择性撤销单个会话或一键撤销全部会话
- 用户被设为 Forbidden 时全部活跃会话被即时撤销
- Realm 数据隔离：仅可操作本 Realm 用户与会话
- 基于 `resource.action` 权限模型的访问控制
- 全部撤销操作可审计

## 4. 业务规则与状态

### 4.1 业务规则

- **Realm 数据隔离**：管理员只能查看和撤销本 Realm 用户的会话，跨 Realm 访问被拒绝
- **主动 kickoff 与账号状态解耦**：管理员主动撤销会话不改账号状态，被下线用户可重新登录；该操作用于即时终止访问，不等于禁用
- **Forbidden 联动撤销**：用户状态被变更为 Forbidden（无论是单独变更还是与其他字段一并编辑保存）时，该用户全部活跃会话被立即撤销；非 Forbidden 的状态变更不触发撤销
- **撤销即时性**：被撤销的会话在其下一次请求时即被判定为未登录，不依赖令牌自然过期
- **权限模型**：会话管理沿用 `resource.action` 模型。本特性的访问控制在 `users.*` 资源命名空间内（参考 [权限管理](../auth/permissions.md)）：会话查看与撤销直接复用既有 **`users.manage`** 权限（该权限已隐含 `users.view`）；仅拥有 `users.view` 的账号不可查看会话列表或执行撤销。不新增权限点。
- **会话可辨识信息**：会话列表至少展示所属 Client App、设备/浏览器（User-Agent）、登录来源 IP、登录时间，便于管理员识别并定位要撤销的具体会话
- **操作可审计**：主动撤销单会话、主动撤销全部会话、以及 Forbidden 联动撤销，均需记入审计日志，**审计 action 统一复用既有 `user.update`**（`AuditAction::UserUpdate`），不新增审计 action。其中管理员主动撤销（单会话/全部）记录在既有 `Session` 目标（`AuditTargetType::Session`）上；Forbidden 联动撤销不产生独立的会话审计记录，而是借用户编辑的 `user.update` 记录在 `User` 目标（`AuditTargetType::User`）上承载，并在 details 中以 `trigger=forbidden_linkage`、`scope=all` 区分来源与范围（检索联动事件时按 `details.trigger=forbidden_linkage` 过滤）。审计记录需包含操作者、目标用户、目标会话（或"全部会话"）与触发来源（管理员操作 / 状态变更联动）。

### 4.2 关键状态与异常

- **无活跃会话**：当目标用户当前没有活跃会话时，会话列表为空，撤销操作不可用或为空操作，管理员得到明确空状态反馈
- **并发撤销**：管理员撤销某会话时，若该会话已被用户自助退出或已自然过期，撤销操作视为对该会话的空操作，不报错
- **目标用户不存在或跨 Realm**：返回拒绝/未找到，不泄露其他 Realm 数据
- **权限不足**：会话管理入口与撤销操作对无 `users.manage`（或同层级）权限的账号不可见/不可用
- **审计目标类型**：管理员主动撤销（单会话/全部）使用 `Session` 目标类型记录；Forbidden 联动撤销作为 `user.update` 记录在 `User` 目标上，凭 `details.trigger=forbidden_linkage` 检索

## 5. 功能需求

### 5.1 核心需求

- 管理员可在用户管理页面进入指定用户的会话管理入口，查看该用户在本 Realm 的全部活跃会话及其可辨识信息（至少含所属 Client App、设备/浏览器 User-Agent、登录来源 IP、登录时间）
- 管理员可对会话列表中的单个会话执行撤销（带确认）
- 管理员可一键撤销该用户全部活跃会话（带确认）
- 用户编辑保存时，若状态被变更为 Forbidden，系统自动撤销该用户全部活跃会话
- 上述撤销操作均记入审计日志，可追溯操作者、目标用户、目标会话范围与触发来源
- 所有操作遵守 Realm 数据隔离与既有权限模型

### 5.2 验收目标

- 拥有会话管理权限的管理员可查看（含所属 Client App、设备 User-Agent、登录 IP、登录时间）、选择性撤销、一键撤销指定用户的活跃会话，且被撤销会话的下一次请求被判定为未登录
- 当用户状态被变更为 Forbidden 时，该用户全部活跃会话被立即撤销（无需等待令牌过期），且该用户此后登录被拒绝并收到禁用提示
- 当用户状态未被改为 Forbidden（含仅在非 Forbidden 状态间变更）时，其活跃会话不被撤销
- 仅拥有用户查看权限的账号看不到会话管理入口与撤销操作
- 跨 Realm 的会话查看/撤销请求被拒绝
- 会话撤销操作可在审计日志中被检索到，记录来源（管理员操作 / Forbidden 联动）

## 6. API 相关约束

**适用性**: 适用

- 用户会话管理接口能力范围包括：查询指定用户的活跃会话列表（返回所属 Client App、设备/浏览器 User-Agent、登录来源 IP、登录时间等可辨识信息）、撤销指定会话、撤销指定用户的全部会话
- 会话管理的访问控制沿用既有 `users.*` 资源命名空间下的 `resource.action` 权限模型，会话查看与撤销**直接复用既有 `users.manage` 权限**（该权限已隐含 `users.view`）；不新增权限点
- 所有会话相关接口必须遵守 Realm 数据隔离，请求方只能访问其所属 Realm 内的用户与会话
- Forbidden 联动撤销作为用户状态变更（用户编辑接口）的副作用实现，不作为独立对外暴露的会话接口；状态变为 Forbidden 时在同一保存事务的语义边界内完成会话撤销
- 会话列表与撤销接口的请求/响应契约、错误模型下沉到技术设计或接口文档维护
- 审计事件复用既有审计写入通道，**审计 action 统一复用既有 `user.update`**；管理员主动撤销（单会话/全部）记录在 `Session` 目标上，Forbidden 联动撤销借用户编辑的 `user.update` 记录在 `User` 目标上（details 中 `trigger=forbidden_linkage`、`scope=all`），凭 `details.trigger` 区分触发来源（管理员操作 / 状态变更联动）

## 7. 前端/交互约束

**适用性**: 适用

- **页面入口**：用户管理页面现有用户行的操作菜单中新增"会话管理 / 强制下线"入口；权限控制可见性（无相应权限的账号不显示该入口）
- **会话列表交互**：从用户行进入会话管理后，展示该用户当前活跃会话列表，每个会话展示所属 Client App、设备/浏览器（User-Agent）、登录来源 IP、登录时间等可辨识信息，便于管理员区分多个会话并定位要撤销的会话；列表为打开时的快照
- **撤销单会话**：会话行提供撤销操作，需二次确认；撤销成功后该会话从列表移除或标记为已撤销
- **撤销全部会话**：列表提供"撤销全部会话"操作，需二次确认；成功后列表清空或全部标记为已撤销
- **空状态**：当用户无活跃会话时，展示明确空状态，撤销操作不可用
- **权限可见性**：会话管理入口与撤销操作仅对拥有相应管理权限的账号可见/可用
- **禁用联动无独立 UI**：Forbidden 联动撤销由用户编辑保存触发，不需要为联动单独提供前端入口；编辑保存成功后可向管理员反馈该用户已被即时下线
- **反馈**：撤销操作成功/失败需有明确反馈；对"会话已被自助退出或自然过期"的并发场景以成功（空操作）处理

## 8. 已确认决策

- **撤销粒度**：会话列表 + 选择性撤销（含一键全部）。新增"列出某用户活跃会话"的管理端能力，支持按会话撤销，也支持一键全部撤销。
- **Forbidden 联动撤销**：用户状态被变更为 Forbidden 时（无论单独变更还是与其他字段一并保存），系统自动撤销该用户全部活跃会话，填补"禁用 ≠ 下线"的安全缺口。该联动在用户状态变更的保存语义内完成。
- **主动 kickoff 与账号状态解耦**：管理员主动撤销会话不改账号状态，被下线用户可重新登录；主动 kickoff 与 Forbidden 联动撤销是两个不同入口，触发方式和账号语义不同。
- **域归属**：core（用户生命周期与运营能力的扩展，与 [用户管理](users.md) 同域）。
- **权限模型**：复用既有 `resource.action` 模型，会话查看与撤销**直接复用既有 `users.manage` 权限**（已隐含 `users.view`），不新增权限点、不引入新的 action 类型（遵循权限管理 PRD "仅 manage/create/view" 的约束）。
- **会话元数据独立索引**：会话列表至少展示所属 Client App、设备/浏览器（User-Agent）、登录来源 IP、登录时间。登录侧捕获的 client_ip 与 User-Agent 以**独立的会话元数据索引**形式存放（**不写入浏览器令牌族记录本体**）供列表读取——这些信息很少被读取，不应污染令牌校验热路径记录。具体索引结构归属技术设计。
- **审计 action 复用 `user.update`**：主动 kickoff（撤销单会话/全部会话）与 Forbidden 联动撤销统一复用既有 `user.update`（`AuditAction::UserUpdate`），不新增审计 action；主动 kickoff 的 target_type 复用既有 `Session`（`AuditTargetType::Session`），Forbidden 联动撤销则借用户编辑的 `user.update` 记录在 `User` 目标（`AuditTargetType::User`）上，以 `details.trigger`（`admin_action` / `forbidden_linkage`）与 `scope`（`single` / `all`）区分触发来源与范围。若后续合规审计要求 action 与 target_type 语义自洽（主动 kickoff 的操作对象是 Session，与字面 `user.update` 存在语义张力），可在本 PRD 调整为新增专用 action（如 `user.session.revoke`）。
