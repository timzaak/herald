## 2. 范围界定

### 2.1 包含功能
- **Per-realm Webhook 订阅管理**：Realm Admin 在管理台为本 Realm 登记多个公网回调地址；每个订阅独立勾选要接收的事件类型类别；订阅支持停用、恢复与删除
- **每个订阅独立的签名密钥**：创建订阅时生成、仅完整展示一次、支持重新生成（轮换）
- **初始事件目录（三类）**：
  1. **用户生命周期**：用户创建（覆盖管理端、扩展接口与公开注册等全部创建来源）、用户禁用、用户注销
  2. **角色授予/撤销**：覆盖管理端手工授予/撤销（含批量角色同步差集）与支付驱动（paywall 履约）的自动授予/撤销，不按来源过滤
  3. **订阅生命周期**：订阅生效、续期、过期、退款
- **投递可靠性承诺**：at-least-once 投递 + 指数退避自动重试 + 每个事件以订阅密钥完成 HMAC-SHA256 签名 + 持续失败自动暂停该订阅并通知 Realm Admin
- **独立的对外集成契约事件模型**：不复用管理员视角的审计记录；事件载荷按数据最小化原则构造
- **接入方集成文档**：签名验证、按事件 ID 幂等、乱序容忍的消费指引与消费示例（官方文档站中英文页面）
- **管理台 Webhooks 管理页**：订阅列表、三态状态与暂停原因可见性、密钥管理与权限门控

### 2.2 不包含功能 (Out of Scope)
- 认证行为事件（登录/登出/登录失败）——高频且与“接入方状态同步”的问题定义错位
- 全量审计目录镜像——审计是管理员视角而非集成契约，PII 脱敏与配置噪声负担全量放大
- 通用事件总线及 Herald 内部事件消费者——不作为本能力范围，避免引入重型内部事件基础设施
- exactly-once 投递语义——不承诺；重复投递是允许的契约行为，接入方以事件 ID 幂等去重
- per-Client-App 粒度的订阅与事件过滤——订阅按 realm 组织，管理面最简且契合 realm 级用户/订阅事件目录；仅在真实接入方提出按 Client App 过滤需求时重新评估
- 手动重放/事件回放管理界面、死信队列查询 API
- 暂停/停用期间事件的补发——恢复订阅后仅投递新事件，缺口由接入方用既有查询 API 自行对账
- 事件增量拉取 API——本功能选定 webhook 推送解决接入方状态同步问题，拉取接口不在本范围
- 组织（org）成员事件外发
- 事件目录之外的补充事件类型（如用户重新启用、订阅取消/暂停/升降级等中间态）——其中订阅取消引发的权益回收信号由角色撤销事件（paywall 联动）覆盖，仅在真实接入方明确需要目录外事件类型时扩展

### 2.3 依赖项
- 既有状态写入点作为触发源：用户生命周期、角色授予/撤销（含 paywall 自动履约）、订阅投影状态机；事件在状态变更生效后触发，不引入新的状态属主
- 既有 RBAC 与 Realm 隔离体系：订阅管理按 `webhooks.view` / `webhooks.manage` 权限门控、事件按 realm 边界扇出
- 既有管理台导航与权限可见性框架（支持主域名与自定义域名双入口挂载）
- Realm 邮件通道（可选依赖）：暂停通知的邮件渠道仅在 Realm 已配置邮件通道时生效；管理台状态可见性不依赖邮件
- 既有入站 webhook 补偿框架的检测-重试工程模式（复用可靠投递思路，不复用入站业务语义）

## 3. 需求概述

### 3.1 功能描述
第三方应用后端（接入方）在缺乏主动通知时无法及时感知 Herald 侧的用户与权益状态变更，只能通过 SDK/API 轮询或自建全量对账，付出轮询配额与对账工程成本，并承受轮询间隔内的状态不一致窗口（例如支付成功但解锁延迟一个轮询周期）。

本功能以 **outbound webhook 事件推送** 解决接入方状态同步问题：Realm Admin 为本 Realm 登记回调订阅并按事件类型类别过滤后，Herald 在用户、角色、订阅状态变更生效时，将带签名的目录内事件推送到匹配的活跃订阅；投递遵循 at-least-once 语义，并具备指数退避重试与持续失败自动暂停保护。接入方在自有后端验签、按事件 ID 幂等消费，将授权判断、provisioning 和 paywall 状态更新从轮询升级为事件驱动。

**两个核心消费场景**：
1. **paywall 秒级解锁**：用户支付成功 → Herald 自动授予 role 并推送角色授予事件 → 接入方后端验签通过后即刻解锁该用户功能，替代轮询窗口
2. **账号禁用即时下线**：Herald 侧禁用用户 → 推送用户禁用事件 → 接入方后端即时下线或冻结该用户在接入方应用内的会话与访问

### 3.2 关键特性
- 状态变更到事件推送的端到端链路：触发 → 事件生成 → 签名 → 投递 → 重试/暂停
- Per-realm 订阅 + 多回调地址 + 事件类型类别过滤
- 行业标准的投递可靠性承诺（at-least-once、指数退避、HMAC-SHA256 签名、自动暂停、管理员通知）
- 作为稳定集成契约的独立事件模型：仅增量演进，破坏性变更必须版本化

## 4. 业务规则与状态

### 4.1 业务规则
- **订阅模型**：订阅属于 Realm，由 Realm Admin 管理；同一 Realm 可登记多个回调地址，每个订阅独立配置事件类型类别过滤；事件按 Realm 扇出到所有匹配且活跃的订阅
- **事件目录**：仅 §2.1 三类目录内的事件会被生成与投递；目录外的状态变更不产生外发事件；角色授予/撤销事件不区分授予来源（管理端与支付驱动同等投递）
- **触发时点**：事件在对应状态变更生效后触发生成与投递；投递结果不影响已生效的业务状态变更本身
- **投递语义**：at-least-once——同一事件可能被投递一次以上，也可能乱序到达；这是契约行为，接入方以事件 ID 幂等去重并容忍乱序（以后到状态为准），Herald 不承诺 exactly-once
- **签名规则**：每个事件以目标订阅的密钥完成 HMAC-SHA256 签名后外发；密钥在创建/重新生成时完整展示一次，此后不回显；轮换后旧密钥立即失效，新事件以新密钥签名
- **回调地址安全底线**：回调地址必须是公网可达地址，私网/环回地址在登记时拒绝；出站外呼同步执行连接时解析公网校验、禁止跟随重定向与限制响应体读取等防 SSRF 安全基线
- **投递失败与自动暂停**：投递收到非成功响应或超时均计为失败并进入指数退避重试；持续失败达到系统判定后，仅暂停该订阅（同 Realm 其他订阅不受影响）并通知 Realm Admin；暂停期间事件不投递、不补发；恢复后仅投递新事件
- **暂停通知**：暂停事实在管理台订阅状态中常驻可见，不依赖邮件；Realm 已配置邮件通道时同时发送通知邮件
- **租户边界**：事件只扇出到本 Realm 的订阅；任何 Realm 的订阅都不会收到其他 Realm 的状态变更事件
- **数据最小化**：事件载荷仅含接入方消费所需的最小信息（稳定标识、事件类型、发生时间、必要业务上下文），不携带管理员视角的审计详情与多余 PII
- **契约稳定性**：事件模型是对外集成契约；后续演进仅做增量变更（新增字段、新增事件类型为非破坏性），破坏性变更必须引入新版本，不得原地修改既有字段语义
- **访问控制**：订阅管理仅对持有 `webhooks.view`（查看）与 `webhooks.manage`（创建/编辑/启停/恢复/轮换/删除）权限的 Realm Admin 开放并遵守 Realm 隔离，两项内置权限默认授予 Realm Admin
- **运行参数不入契约**：退避曲线、持续失败判定阈值、投递并发上限、重试风暴防护参数均为可调运行参数，不构成对外产品契约承诺

### 4.2 关键状态与异常
- **订阅状态**：
  - **活跃**——正常接收匹配事件
  - **暂停（系统自动）**——持续投递失败触发，不投递事件；可由 Realm Admin 恢复（不能由管理员手动设为暂停）
  - **停用（管理员手动）**——管理员主动停用，不投递事件；可重新启用
  - 删除订阅后不再接收事件，登记信息按管理台删除交互移除
- **投递异常路径**：非成功响应/超时 → 指数退避重试 → 持续失败 → 自动暂停 + 通知 → 管理员处置后恢复 → 仅投递新事件
- **密钥轮换异常**：轮换后旧密钥立即失效（不保留双密钥过渡窗口）；接入方未同步更新密钥会导致验签失败，官方文档指引接入方先更新验签密钥再执行轮换
- **扇出风暴防护**：多订阅 × 事件积压的放大由并发上限、每轮认领上限与自动暂停机制共同约束
- **观察期（去留条件）**：发布后观察真实订阅与使用信号；若观察期内持续零订阅零询问，则按既定去留条件降级为“事件日志拉取”轻方案或归档，不继续扩展事件目录

## 5. 功能需求

### 5.1 核心需求
- 订阅全生命周期管理：登记（公网地址 + 类别过滤）、查看、编辑、停用/启用/恢复、删除、密钥重新生成
- 目录内事件的完整触发覆盖：三类目录对应的每个状态变更都会生成事件并投递到匹配活跃订阅
- 投递管道：签名外发、at-least-once、指数退避重试、持续失败自动暂停、暂停通知（管理台常驻 + 条件邮件）
- 接入方集成文档：验签方法、幂等与乱序处理指引、两个消费示例（paywall 秒级解锁、账号禁用即时下线）
- 管理台 Webhooks 管理页与权限可见性

### 5.2 验收目标
- **端到端线 1（paywall 解锁）**：用户支付成功后，订阅方收到对应的角色授予事件（验签通过、秒级到达），接入方据此解锁功能，全程无需轮询
- **端到端线 2（禁用下线）**：Herald 侧禁用用户后，订阅方收到用户禁用事件
- 事件类型过滤与 Realm 隔离正确：未勾选类别的事件不投递；其他 Realm 的状态变更不产生任何投递
- at-least-once 生效：接入方短暂故障恢复后，积压事件最终送达；重复投递可被接入方按事件 ID 去重
- 持续失败自动暂停仅影响该订阅，暂停状态在管理台可见，已配置邮件通道的 Realm 收到通知邮件；恢复后新事件正常投递且不补发暂停期间事件
- 签名密钥仅创建/重新生成时完整展示一次；轮换后新事件以新密钥签名
- 私网/环回回调地址在登记时被拒绝（前端行内预校验 + 服务端权威拒绝）
- 事件载荷为独立集成契约模型：不含审计详情与多余 PII
- 观察期结束时按去留条件评估使用信号并记录结论

## 6. API 相关约束

**适用性**: 适用

- **能力范围**：出站事件推送（系统到接入方的签名回调）与订阅管理（查询、创建、编辑、状态切换、密钥轮换、删除）；不提供事件拉取、回放或死信查询类接口
- **访问控制**：订阅管理走 Realm Admin 权限面（`webhooks.view` / `webhooks.manage`）并遵守 Realm 隔离；事件外发是系统行为，不经过用户请求-响应面；不扩展外部 API / SDK 能力面
- **集成契约与接口说明**：事件模型与签名方案是对外集成契约，遵循 §4.1 契约稳定性规则；具体事件目录、信封格式、签名头与消费指引以官方文档站集成文档（`/en/docs/integration/webhooks` 与 `/zh/docs/integration/webhooks`）为准，管理接口明细由服务 OpenAPI 规范承载
- **安全边界**：出站外呼目标为租户可控 URL，登记阶段拒绝私网/环回地址，投递阶段执行连接时解析公网校验、禁止重定向与响应体读取限制等防 SSRF 基线
- **兼容性**：本功能为纯新增能力面，不改变既有入站 Provider webhook、补偿框架与审计日志的语义

## 7. 前端/交互约束

**适用性**: 适用

- **页面入口**：管理后台左侧导航新增 Webhooks 菜单，对持有 `webhooks.view` 权限的 Realm Admin 可见，同时支持主域名（含 Realm 前缀）与自定义域名两种管理台入口；无权限者菜单不可见，直接访问时展示无权访问提示；写操作入口受 `webhooks.manage` 权限控制
- **关键交互**：
  - 订阅列表：展示回调地址、事件类型类别、三态状态（活跃/系统暂停/手动停用）、暂停原因入口、密钥末位提示与创建时间
  - 新建/编辑订阅：公网回调地址 + 三类事件类别勾选；明显私网/环回地址在提交前即行内拒绝并提示原因（不发起请求），域名解析私网等情形由服务端拒绝兜底
  - 密钥管理：创建与重新生成后进入一次性密钥展示页完整展示密钥并提示妥善保存（支持一键复制）；刷新或缺少会话状态直接访问该页时自动返回列表；列表与编辑页仅展示密钥末位提示，不回显完整密钥
  - 停用/启用/恢复/删除：状态切换为直接操作并按当前三态映射对应动作（活跃→停用、暂停→恢复、停用→启用），带结果反馈；删除与密钥轮换均需二次确认
- **状态反馈**：自动暂停的订阅在列表中常驻标识并可查看失败摘要、连续失败次数、暂停时间与“恢复后不补发”说明；当列表存在暂停订阅且 Realm 未配置邮件通道时，页面展示邮件渠道不可用说明（管理台可见性不受影响）
- **接入方侧无 Herald UI**：面向接入方的可见面是官方文档站的集成文档与消费示例；接入方回调端点由接入方自行实现与运营
