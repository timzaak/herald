## 2. 范围界定

### 2.1 包含功能
- 多次部分退款的积分回收：Stripe 与 Creem 两条充值退款路径均以「单笔退款增量」为单位按比例回收积分，多次部分退款的累计回收对齐累计退款比例
- 一次性购买（充值/买断）的角色回收规则：部分退款保留角色，累计退款达到原支付金额 100% 时回收
- 退款回收幂等以「支付方退款单」为单位：同一退款单重复推送不二次回收积分；角色回收为幂等操作，重复推送时按已记录的闸门状态重跑（对已回收角色为无操作），作为此前 best-effort 回收失败后的自愈重试

### 2.2 不包含功能 (Out of Scope)
- 订阅退款政策调整：任意金额退款→立即整单取消（撤销订阅配额权益与订阅关联角色）维持既有政策
- 历史回溯补偿：不回溯调整历史已执行的积分回收，不恢复历史因部分退款被回收的角色；个案由管理员走既有手动调整途径
- 发票与 credit note 层：多次部分退款（累计入账、超额拒绝、作废回冲）为既有能力，无改动
- 争议（dispute）与撤销事件处理：一次性购买的争议/撤销事件不触发角色回收（Stripe、Creem 的争议处理均仅覆盖订阅）；「争议事件回收一次性角色」的能力缺口另立方案（`DEC-refund-patch-005`）
- WeChat 渠道退款信号：该渠道无退款信号源，维持既有渠道级例外
- 前端页面与管理后台界面变更

### 2.3 依赖项
- Stripe / Creem 退款 webhook 信号（退款单标识与金额）
- 支付尝试快照（退款回收归属积分账户的解析依据），缺失时拒绝处理（fail-loud），不做模糊回收

## 4. 业务规则与状态

### 4.1 业务规则
- **规则 1（单笔增量回收）**：每笔退款按其金额占原支付金额的比例回收该来源授予的积分；比例计算允许四舍五入到整数积分。
- **规则 2（只回收未消费）**：单笔回收上限为该来源当前未消费余额；回收不产生负余额，不影响用户其他来源（订阅、免费发放、管理员发放）的积分。
- **规则 3（单笔退款幂等）**：同一笔退款重复推送（重试、重发）不产生二次回收；不同退款事件各自独立回收。
- **规则 4（累计全额回收）**：累计退款金额达到原支付金额时，回收该来源全部剩余积分。
- **规则 5（角色回收全额阈值）**：一次性购买（充值/买断）授予的支付来源角色，在部分退款（任意比例、无论几笔）下保留；仅当该笔支付累计退款达到原支付金额 100% 时回收。管理员手工授予的同名角色不受影响（既有规则）。
- **规则 6（争议/撤销例外）**：支付方的争议、撤销类事件不是退款，不受规则 5 的保留约束；其处理维持既有事件行为：一次性购买的争议事件不回收角色（Stripe、Creem 的争议处理均仅覆盖订阅），订阅争议走既有订阅状态流（`DEC-refund-patch-005`）。
- **规则 7（订阅退款不变）**：订阅的任意退款维持「立即取消并撤销订阅权益」既有政策，不引入按比例保留。
- **规则 8（不回溯）**：回收规则对规则生效后到达的退款事件适用；此前已执行的回收与角色状态不做回溯调整。

### 4.2 关键状态与异常
- **退款回收归属失败**：无法解析退款对应的支付尝试（快照缺失、realm 不匹配）时，拒绝处理（fail-loud），不做模糊回收。
- **渠道差异**：Apple/Google IAP 的退款为整笔交易语义（天然全额），行为与规则 4/5 一致，无需单独分支；WeChat 无退款信号，维持既有例外。
- **发票层退款账目**（credit note 累计入账、超额拒绝、作废回冲）与积分回收相互独立。

## 5. 验收目标

- US-RC-001 场景 1–4 全部通过（含 300+200 两笔部分退款累计回收 50% 的锚定场景）。
- US-RC-002 场景 1–4 全部通过（部分退款保留角色、累计全额回收角色、争议事件不触发回收且保留不失效）。
- 既有单次部分退款、单次全额退款、退款幂等、多积分账户归属回收相关既有测试全部保持通过（回归）。
- 订阅退款立即取消的既有行为与测试不受影响（回归）。

## 6. 边界与约束

**适用性**: 不适用（原 API 约束与前端/交互约束均不适用，合并陈述）

本 PRD 为支付方 webhook 处理链路与内部回收逻辑的行为规则，不新增、不变更任何对外接口；管理员手动 credit note 记录接口与发票查询接口维持现状。无前端页面与管理后台界面变更；退款回收流水在既有交易历史中按每笔退款的正确金额展示（US-PO-003 既有能力）。

## 7. 已确认决策

> 本节只收录当前有效的决策与未决问题，记取舍、理由、决策人与重开条件；规则正文只在 §4 定义，DEC/Q 编号保持稳定，供代码注释、测试与跨 PRD 引用追溯。DEC ID 前缀沿用原 feature 名 `refund-patch`（与 PRD 文件名 `refund-clawback` 不同），保持原样供追溯。

- **DEC-refund-patch-001 · 回收范围**（user，2026-09-14 会话确认）：积分回收增量语义 + 一次性购买角色回收细化；订阅退款政策维持现状。理由：多次部分退款积分过度回收（Stripe 路径把累计退款额当单次退款额使用）是确定的资金正确性 bug；角色回收细化为用户要求；订阅粗粒度政策在业界主流范畴内（Stripe Entitlements 亦为退款不自动撤权）。落点：§2。重开条件：出现订阅部分退款需按比例保留权益的真实需求。
- **DEC-refund-patch-002 · 角色回收全额阈值**（user，2026-09-14 会话确认）：部分退款保留角色，仅累计退款达 100% 回收；争议/撤销不受约束（规则正文见 §4.1 规则 5/6）。理由：部分退款通常是商家善意补偿，不应剥夺购买凭证；退款由商家主动发起，大比例退款保角色的滥用风险可控；与主流做法一致。落点：§4.1 规则 5/6。重开条件：出现部分退款套利（大比例退款保角色）的实际滥用案例。
- **DEC-refund-patch-003 · 积分回收增量语义**（user，2026-09-14 会话确认）：以单笔退款增量为单位按比例回收，累计回收对齐累计退款比例，幂等以退款单为单位（规则正文见 §4.1 规则 1/3/4）。理由：修复 Stripe charge.refunded 累计值被当增量使用的过度回收；Creem 路径已是该语义，本决策将其固化为全渠道不变量。落点：§4.1 规则 1/3/4。重开条件：支付方退款事件语义变更。
- **DEC-refund-patch-004 · 历史不回溯**（user，2026-09-14 会话确认）：不补偿历史过度回收积分与被回收角色，仅对未来退款事件生效（规则正文见 §4.1 规则 8）。理由：历史回收与消费交错无法精确重建差额；角色状态可能已被后续事件覆盖（重新购买、订阅变化），批量回补有二次错误风险。落点：§4.1 规则 8、§2.2。重开条件：出现可批量精确重建差额的可靠数据源。
- **DEC-refund-patch-005 · 争议维持现状**（user，2026-09-14 会话确认）：争议/撤销事件处理不变（一次性争议不回收角色）；US-RC-002 场景 4 钉住现状；能力缺口另立方案（规则正文见 §4.1 规则 6）。理由：澄清 DEC-002「维持照常回收」的事实基线：代码现状并无一次性争议回收可「照常」，实现它需设计 dispute created/lost/won 生命周期，超出本正确性修复的范围；DEC-002 的保留规则豁免部分不变。落点：§4.1 规则 6、§2.2、§5。重开条件：一次性购买争议回收的真实需求出现并另立方案。
