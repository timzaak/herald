# 组织授权（Organization）产品需求文档 (PRD)

**创建时间**: 2026-10-13
**优先级**: P1

> 场景背景：下游应用在产品内部普遍存在实例级分组（参照 OnceWise Flow 的 workspace）——同一用户在不同分组里持有不同角色，成员由应用邀请、提升和移除；Herald 既有 RBAC 是 (realm, Client App, resource, action) 的扁平模型，没有实例维度，无法表达这种「角色随实例变化」的授权。本 PRD 在已发布扁平 RBAC 基线（`docs/prd/auth/permissions.md`）之上新增一个**独立的实例级授权能力层**——组织（Organization）：应用后端把应用内分组映射为 Herald 组织，由 Herald 托管成员与角色，并在用户请求时提供组织级判定；一次实现、所有 Client App 共用，应用不再各自实现成员表与角色检查。本层与扁平 RBAC 的规则互不引用、互不调和（层间隔离见 §4.1）；唯一交叉点是内置 realm-admin 网格加法式新增 `orgs.view` / `orgs.manage` 两个权限项，作为组织能力面的开通通路（见 §2.2、§6、§7）。本文档不承载接口端点、请求/响应 schema、HTTP 状态码、数据库建表/迁移或代码类型定义；技术方案细节参见对应技术设计。

## 2. 范围界定

### 2.1 包含功能

- **组织实体与应用侧映射**：组织从属于唯一的 (realm, Client App)；每个组织登记应用侧标识，与应用内分组（workspace、团队等）一一映射；产品概念为通用「组织」，应用语义经应用侧标识表达
- **组织生命周期**：组织的创建（登记应用侧标识、指定 owner）与删除由应用后端驱动，与应用内分组生命周期同步；Herald 不主动创建组织
- **组织成员关系托管**：添加 / 移除 / 变更角色 / 查询成员与成员列表，幂等语义（见 §4.1）
- **组织角色**：内置 owner / admin / member 三档；角色能力词表沿用 `resource.action` 精确匹配与既有 action 层级语义，由应用与 realm 管理员经现有角色定义能力配置（首版对自定义档位挂载词表的限制见 §2.2）
- **组织级判定**：对「用户 × 组织」返回角色标签与按角色解析的能力判定（布尔）两种结果形态；非成员为明确结果形态
- **按用户查询组织列表**：返回某用户在某 Client App 下加入的全部组织及角色
- **面向应用后端的能力面**：以上能力以绑定 Client App 的 client 凭证（API Key）认证调用；读操作要求 `orgs.view`、写操作要求 `orgs.manage` 扁平策略，realm 管理员经现有管理台将其授予应用凭证
- **以应用用户名义发起的成员变更**：应用后端可指定被代表用户发起变更，依次通过组织管理门、自持门与所有权转移门（US-OA-005）
- **安全不变量**：层间隔离、组织间隔离、组织内反提权、owner 与最后管理员保护（见 §4.1）
- **生效语义**：成员与角色变更近即时反映到组织判定
- **审计**：组织与成员的关键操作进入审计日志，记录发起方（client 凭证或被代表用户）

### 2.2 不包含功能 (Out of Scope)

- **邀请流程**：邀请 UX、邀请码/链接、邀请邮件品牌、落地页——全部由应用自持；Herald 只提供幂等的成员管理能力
- **Herald 管理台组织浏览页**（realm 管理员查看/治理组织的界面）与**面向下游的轻量批量判定端点**：延后至出现首个真实消费方时另行立项
- **自定义档位挂载应用自定义资源词表的通路**：首版词表配置豁免仅覆盖内置三档（见 §4.1 组织角色），自定义档位通路延后
- **组织嵌套层级与对象级权限**：不引入子组织、不引入组织内单条资源的 ACL
- **组织与计费/配额联动**：按组织数计费、成员数限额等不在本 PRD 范围
- **对现有扁平 RBAC 既有资源的任何行为修改**：既有资源的检查入口、缓存行为、防提权规则与权限清单零变化；唯一例外是内置 realm-admin 网格加法式新增 `orgs.view` / `orgs.manage` 两个权限项（存量 realm 一次性迁移回填），用于解除组织面首笔授予的「授予方自持」死锁（见 §7）
- **把组织实例编码进权限词表**：不出现 `workspace:{id}:admin` 一类实例化权限串；实例语义只存在于组织与成员关系
- **Herald 自身的前端改动**：组织与成员的最终用户交互全部属于应用侧 UX

### 2.3 依赖项

- **Client App 体系**：组织能力面以绑定 Client App 的 API Key 调用；Client App 的注册、禁用与凭证管理沿用现状
- **现有角色/权限元数据能力**：组织角色的定义、能力词表与解析语义复用现有元数据层（`docs/prd/auth/permissions.md`），不另建第二套定义系统
- **账号体系**：组织成员是 realm 内账号；账号状态与组织判定联动（§4.2）
- **审计体系**：组织与成员操作复用现有审计通道
- **缓存设施**：组织判定使用独立缓存参数并支持变更显式失效（实现层）

## 4. 业务规则与状态

### 4.1 业务规则

**组织归属与映射**：
- 组织从属于唯一的 (realm, Client App)；组织不可跨 realm，同一组织内不可混用不同 Client App 的语义
- 每个组织登记应用侧标识；同一 Client App 下，一个应用侧标识至多关联一个组织，重复创建按幂等处理（返回既有组织，不产生第二个组织）
- 组织的创建与删除由应用后端驱动（与应用内分组生命周期同步）；Herald 不主动创建组织

**组织角色**：
- 内置三档：owner（创建组织时登记于创建方指定账号）、admin、member
- 角色的能力词表沿用 `resource.action` 精确匹配与既有 action 层级规则（`manage` 向下隐含），词表内容可由应用与 realm 管理员经现有角色定义能力配置
- 内置三档初始为空能力词表（Herald 无法预知应用资源名），开箱判定全 false 为文档化预期，接入方需先配置词表
- 向内置三档挂载策略词表时豁免扁平防提权的「授予方自持」（应用自定义资源在扁平层无人自持过，不豁免则词表永远无法配置）；豁免仍保留策略管理权限门、realm 作用域与通配符拒绝，且仅限内置三档（内置档位不可由管理员伪造）
- 应用可经现有角色定义能力扩展额外档位（如「可编辑」）；扩展档位与内置档位在判定语义上平等，仅内置档位受本节保护规则约束

**层间隔离（安全边界）**：
- 组织级判定**只**依据该用户在该组织内的角色；扁平 `user_roles`（含 `realm-admin` 等平台角色）不参与组织判定
- 管理权 ≠ 成员权：Herald/realm 管理员身份不自动产生任何组织内权限（US-OA-006）
- 应用需要「扁平权限 ∪ 组织权限」的并集语义时，自行分别判定后合并，Herald 不代为并集

**组织间隔离**：
- 用户在组织 A 的角色对组织 B 的判定无任何影响；一切组织判定与成员管理都以单一组织为界

**组织内反提权**：
- 在组织内授予或变更角色时，发起方（被代表的用户，或直接以 client 凭证发起的应用）必须在该组织内自持被授予角色所含的能力
- client 凭证直接发起视为应用对其自有组织的完整管理权；以应用用户名义发起（指定被代表用户）时，依次通过组织管理门（admin/owner 档位）、自持门与所有权转移门
- 该规则是扁平防提权「授予方自持」在组织维度的对应物：自持以组织为界，不在扁平层求值

**owner 与最后管理员保护**：
- owner 不可被移除出组织、不可被降级
- 任何成员变更操作不得使组织失去全部 admin 及以上角色的成员；违反时拒绝并提示先转移管理权。组织恒保有 owner（owner 受不可移除/降级保护），使该规则在正常状态下结构性成立，保护逻辑仍作为变更门守卫存在
- owner 身份的转移属于组织内角色变更，受上述规则与反提权约束；转移为原子操作，原 owner 落为 admin 档位

**成员资格**：
- 成员必须是组织所在 realm 内的账号；跨 realm 账号不可加入（US-OA-002 场景 3）
- 添加成员为幂等 upsert：重复添加同一账号时，不产生重复成员关系；指定角色与原角色不一致时更新为新角色

**生效语义**：
- 成员与角色的变更近即时反映到组织判定（实现层以独立短缓存 + 变更显式失效保障）
- 管理台调整档位能力词表后，组织判定在短暂陈旧窗口内跟进；具体窗口时长属实现层运行参数
- Herald 不因成员变更主动吊销用户的既有登录态；应用侧如何处理被移除成员的存量会话由应用决定

**删除级联**：
- 组织被删除时，其全部成员关系与角色随之失效；按用户查询组织列表不再包含该组织
- 成员账号被删除时，其组织成员关系随之失效

**审计**：
- 组织创建/删除、成员添加/移除/角色变更，以及成员管理操作被拒绝的关键事件进入审计日志，记录发起方（client 凭证或被代表用户）、组织与目标成员
- 读判定不逐请求落账（防审计洪泛），以可观测日志留痕

### 4.2 关键状态与异常

- **非成员判定**：对非成员的组织判定返回明确的非成员结果，不与「无权限」混淆；应用据此自行决定拒绝或只读
- **账号状态联动**：成员账号处于禁用或删除状态时，组织判定按拒绝处理，即使成员关系记录仍在
- **Client App 禁用联动**：Client App 被禁用后，其组织能力面不可用，判定按拒绝处理
- **凭证与调用方越权**：组织能力面要求绑定 Client App 的 API Key，未绑定 Client App 的凭证不具备组织能力面访问权；调用方不具备目标组织的成员管理能力时，操作被拒绝
- **存在性探测防护**：对无权调用方，「组织不存在」与「无权限」的响应口径一致，不泄露组织的存在性与成员构成
- **幂等冲突**：重复创建组织、重复添加成员均按 §4.1 幂等规则处理，不产生重复数据，也不静默吞掉角色差异
- **分页参数越界**：成员列表的分页参数越界被拒绝（fail-loud），不静默截断

## 5. 验收目标

- 应用后端持绑定 Client App 的 client 凭证可完成「创建组织 → 添加成员 → 组织判定 → 变更角色 → 移除成员」的完整闭环，全程无需 Herald 管理台逐次介入
- realm 管理员可经现有管理台将组织面权限（`orgs.manage`）授予应用凭证；未获授予的凭证在组织能力面被拒绝（负向验证）
- 内置档位的能力词表可经现有管理台配置并驱动组织判定；非内置角色不享有词表挂载的自持豁免（负向验证）
- 组织判定正确区分同一用户在不同组织的不同角色（实例级语义成立）
- 层间隔离与组织间隔离成立：仅持平台管理身份的主体在组织判定中得到非成员结果；组织 A 的角色不影响组织 B 的判定（负向验证）
- 组织内反提权成立：不具备组织内自持能力的发起方无法完成角色授予（负向验证）
- owner 保护与最后管理员保护成立：相应操作被拒绝且组织不失去管理者；owner 转移为原子操作
- 成员移除后组织判定近即时变为非成员，不存在可感知的延迟窗口
- 现有扁平 RBAC 与管理台行为零回归：扁平权限检查、防提权、内置角色保护的行为与本能力上线前一致（realm-admin 清单新增 `orgs.*` 两行除外）
- 组织与成员的关键操作可在审计日志中追溯到发起方（client 凭证或被代表用户）

## 6. 边界与约束

**适用性**: 部分适用（API / 集成边界适用；前端/交互约束不适用——本能力无 Herald 自身前端改动，组织与成员的最终用户交互全部属于应用侧 UX，由应用经 Herald 能力实现；Herald 管理台的组织浏览页为后续阶段，届时另行立项）

**API / 集成边界:**
- **能力面与认证**：组织能力面向应用后端开放，以绑定 Client App 的 API Key 认证；能力范围限于 §2.1 所列（组织生命周期、成员管理、组织判定、按用户列组织），与现有面向应用的 ext 能力面同族并列
- **策略门**：读操作要求 `orgs.view`、写操作要求 `orgs.manage` 扁平策略；两项随内置 realm-admin 角色加法式下发（存量 realm 一次性迁移回填），realm 管理员经现有管理台授予绑定 Client App 的应用凭证
- **realm 边界**：组织、成员、判定均在单一 realm 内闭合；成员必须为该 realm 账号；不存在跨 realm 的组织操作；client 凭证只能操作其所属 Client App 的组织
- **与现有权限检查的关系**：现有扁平权限检查（管理端与 ext 端）的语义、缓存行为与响应契约不变；组织判定是并列的新判定入口，不修改任何既有检查结果
- **兼容性**：本能力上线不改变现有 Client App、API Key、用户角色分配的任何行为；未使用组织能力的应用无感知
- **安全口径**：判定与成员管理接口遵循 §4.2 的存在性探测防护
- **性能语义**：组织判定面向下游每请求调用模式，满足成员变更近即时生效；具体缓存参数属实现层，不在本 PRD 约定

## 7. 已确认决策

> 本节只收录当前有效的产品级取舍，规则正文只在 §4 定义，此处不复述。

- 组织授权采用 Herald 托管的通用平台层：组织、成员与判定均为 Herald 托管的通用实体，应用内分组语义经应用侧标识映射；不做应用自持成员体系的过渡方案。理由：实例级分组是多个下游应用的共性需求，平台化一次实现后所有 Client App 共用
- 成员关系与组织判定是与扁平 RBAC 并立的独立模块：两层只共享角色/权限词表与策略解析语义；扁平层既有资源的检查入口、缓存与防提权零改动。唯一例外：内置 realm-admin 网格加法式新增 `orgs.view` / `orgs.manage`（存量 realm 迁移回填）——「授予方自持」规则使组织面首笔授予在现有管理台不可完成，不加该种子则组织能力在真实部署不可达
- 组织判定只依据组织内角色，不并集扁平 `user_roles`；平台管理身份不自动获得组织内权限（管理权 ≠ 成员权）。理由：防跨层提权，平台管理员不应默认穿透应用内数据边界；需要并集语义的应用自行两次判定后合并
- 邀请流程留在应用侧，Herald 只提供幂等的成员管理能力。理由：邀请的品牌、流程与落地体验属于应用，Herald 托管通用邀请必然别扭且扩大模块面
- 内置三档组织角色挂载策略词表豁免「授予方自持」：应用自定义资源名在扁平层无人自持过，不豁免则词表永远配不进去；豁免仍保留策略管理权限门、realm 作用域与通配符拒绝，且仅限内置三档（内置档位不可由管理员伪造），自定义档位词表通路延后
