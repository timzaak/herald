## 2. 范围界定

### 2.1 包含功能

- **手机号作为并列登录标识**：开启后，手机号与 email/username 并列，可用于密码登录标识分流与短信验证码登录；email 仍为账户必填身份，`account.email` 既有链路不变。重点服务中国国内场景（手机号优先的用户习惯与短信可达性）。
- **短信验证码登录**：对已绑定且已验证手机号的账号，提供两阶段（发送/验证）验证码登录；登录成功按既有客户端会话方向（Bearer access/refresh token）签发会话。
- **账户手机号自助管理**：已注册用户在 Security 设置中绑定手机号（短信验证码验证占有）、换绑（reauth + 新手机验证码验证）与解绑（reauth）。
- **Realm 级短信通道配置**：短信服务商（阿里云=国内、Twilio=国际）通道配置由 Realm 管理员在本 Realm Settings 中管理，含服务凭证、签名名/模板标识与默认国家码；凭证脱敏展示；配置变更记审计；提供测试短信以验证通道。
- **单一「手机号登录」Realm 开关**：同时覆盖手机号作为密码登录标识与短信验证码登录；开启前提为本 Realm 短信通道已配置（fail-closed）；关闭后平滑降级。
- **管理端用户手机号处置**：用户列表/详情脱敏展示、按手机号搜索、解绑（二次确认+审计）与换绑（新手机验证码验证后生效）。
- **防滥用**：Client App 级 Turnstile 前置 + IP 与手机号双维度独立限流（收紧于 email），验证码一次性消费、尝试上限、新码覆盖旧码。
- **隐私与合规联动**：手机号全链路脱敏展示（`138****8000` 形式）；自助注销的匿名化管线同步处理手机号列。

### 2.2 不包含功能 (Out of Scope)

- **无邮箱的纯手机号账号**：不引入无邮箱账户模型；手机号始终是 email 之外的并列标识。
- **手机通道无邮箱自动注册**：未注册手机号发起短信验证码登录不创建账户，返回未注册提示或引导到注册入口。
- **注册流程收集手机号**：注册表单不变，手机号仅通过注册后自助绑定获得。
- **SMS 二次认证 / MFA 因子**：不触碰 TOTP 的 SMS 因子边界（[TOTP 二次认证](totp.md) §2.2 的 out of scope 保持不变）；短信验证码仅为第一因素登录入口。
- **SMS 正文本地模板渲染**：短信签名与正文模板归属服务商侧报备，Herald 不提供 SMS 正文编辑能力（email_templates 模式不扩展到 SMS）；realm 配置只承载签名名/模板标识/凭证，验证码作为模板变量传递。
- **不活跃账号二次放号二次验证**：与 email OTP 同等信任模型，不增加流程分支（留待后续迭代）。
- **其他短信服务商**：v1 仅阿里云 + Twilio；腾讯云等按同一通道抽象后续扩展。
- **具体限流/有效期数值**：运行参数不属于 PRD 契约，由技术设计以固定值测试锚定。
- **首期限定特定 Realm**：不做运营侧硬性投放限定，per-Realm 默认关闭。

### 2.3 依赖项

- **Client App 级 Turnstile 防护**（防护层级下放依赖）：短信验证码发送的人机验证按当前请求绑定 Client App 的 Turnstile 配置执行，与邮箱验证码登录同口径；配置能力由 Client App PRD 承载（见 [Client App 管理](../integration/client-app.md)）。
- **现有协议同意模型**：复用"登录即同意/协议更新重新确认"既有语义（见 [合规适配](../core/legal-consent-account-deletion.md)）；本功能不新增同意模型（无自动注册路径，不引入注册即同意新分支）。
- **Realm Config 配置体系**：短信通道与「手机号登录」开关纳入 Realm Config 管理与权限门禁（见 [Realm 设置](../core/realm-settings.md)，对齐邮件服务先例）。
- **现有用户与账户基础设施**：账户状态枚举、注册政策、标识唯一性与注销匿名化管线（见 [用户管理](../core/users.md)）。
- **自建用户 UI 的 Bearer 登录能力**：短信验证码登录成功签发的会话按 Bearer access/refresh token 方向建立（见 [自建用户 UI](../integration/custom-user-ui.md)），本 PRD 只声明依赖。
- **外部短信服务商**：阿里云（国内）与 Twilio（国际）账号、签名与模板报备由租户自备。

## 4. 业务规则与状态

### 4.1 业务规则

- **标识与身份**：手机号是与 email 并列的登录标识；email 仍为账户必填身份与恢复渠道；不引入无邮箱账户。注册流程不收集手机号，手机号仅经注册后自助绑定获得。
- **规范化与唯一性**：手机号统一规范化为 E.164 形式后存储与比对；未带国家码的输入按 Realm 默认国家码解析（默认国家码为「手机号登录」配置的组成部分）；唯一性粒度为同 Realm 内的规范化手机号，与 email/username 一致；绑定/换绑时与同 Realm 既有手机号冲突则拒绝。格式或号段非法的输入返回统一错误，不区分具体失败原因（防探测）。
- **能力开关**：单一「手机号登录」Realm 开关，开启后同时生效：① 密码登录标识分流接受手机号；② 短信验证码登录入口。开关 fail-closed：短信通道未配置或配置不完整时，开关不可开启——控制台禁用并提示原因，API 侧拒绝写入（对齐 email_otp"未配置邮件不可开启"口径）；关闭方向不受限。关闭后平滑降级：已绑定用户仍可用密码/TOTP/Passkey 登录，已绑定手机号数据保留，重新开启后无需再次绑定。
- **绑定与占有验证**：绑定手机号必须通过向该手机号发送验证码并验证成功来证明占有；仅验证过的手机号可用于登录（已绑定 = 已验证占有）。自助绑定/换绑/解绑均为敏感操作：需先完成 reauth（密码/TOTP/Passkey 任一因素），且仅限用户本人第一方浏览器会话发起（对齐自助改邮箱边界，见 [用户管理](../core/users.md) §4.1）。换绑 = reauth + 新手机号验证码验证 + 唯一性检查。
- **短信验证码登录流程**：两阶段（发送/验证），结构与邮箱验证码登录对齐：验证码一次性消费、新码覆盖旧码、连续错误达上限作废该次验证码；仅对已绑定且账号状态可登录的用户有效。登录成功按 Bearer 会话方向签发；不得绕过二因素（TOTP/Passkey 任一启用即进入二阶段验证）与高危操作 reauth。凭证定位与 email OTP 一致：便利入口，非强认证。
- **未注册/未绑定分支**：手机号在当前 Realm 不匹配任何账号时，不发送验证码、不创建账户，返回未注册提示或引导到注册入口/其他登录方式。防枚举口径与 email OTP 一致：对存在但非激活（禁用等）的账号，发送反馈与正常发送一致，不暴露差异。
- **账号状态约束**：被禁用账号即使验证码正确也拒绝登录，提示账号已被禁用。
- **短信通道配置**：服务商（阿里云/Twilio）、凭证、签名名/模板标识与默认国家码由 Realm 管理员在本 Realm 配置；凭证类字段展示时脱敏、仅编辑时接受明文（对齐邮件配置先例）；短信正文模板归属服务商侧，Herald 不提供正文编辑；配置变更记审计；提供测试短信（受频率限制）验证通道可用性。
- **管理端处置**：用户列表/详情以脱敏形式展示手机号；支持按完整手机号（规范化匹配）搜索；解绑需二次确认并记审计；换绑需向新手机发送验证码并验证成功后生效，验证未完成前旧绑定保持不变，维持"已绑定手机号 = 已验证占有"不变式。管理端处置不受「手机号登录」开关限制（账号数据事后处置语义）。
- **防滥用**：验证码发送按当前请求绑定 Client App 的 Turnstile 配置前置人机验证；IP 与手机号双维度独立限流，收紧于 email 口径（具体数值不属 PRD 契约）；验证码尝试次数与有效期设上限。
- **隐私与注销联动**：手机号在所有用户可见界面（含管理端列表、本人 Security 页）以 `138****8000` 形式脱敏展示，脱敏一律由服务端派生；自助注销的匿名化管线同步处理手机号，口径与 email 匿名化一致。
- **Realm 隔离**：短信通道与开关配置、用户手机号查询与处置均限定在本 Realm 内，跨 Realm 访问被拒绝。

### 4.2 关键状态与异常

- **验证码错误/过期/重复使用**：统一错误语义，类别区分由响应消息文本承载（无结构化错误码）；达到连续错误上限后该次验证码作废。
- **发送频率受限**：返回 429 语义，不发送新验证码；用户可见文案由前端本地化承载。
- **绑定/换绑手机号冲突**：规范化后与同 Realm 既有手机号重复时拒绝并提示已被使用。
- **短信发送失败/通道故障**：不视为登录或绑定成功；给出明确失败反馈；登录场景保留密码等其他方式回退；通道配置状态可经管理端检查（对齐 EmailConfigStatus 模式）。
- **Realm 未开启手机号登录**：登录页不展示短信验证码入口，密码登录不接受手机号标识；已绑定用户走既有方式；本人 Security 页保留已绑定手机号的只读展示（平滑降级语义）。
- **短信通道未配置**：Security 页不展示绑定入口（或说明原因），直接发起被明确拒绝而非假成功（与自助改邮箱、email OTP 启用的未配置门控口径一致）。
- **跨 Realm 访问配置或用户**：被拒绝。

## 5. 验收目标

- 已绑定手机号的正常状态用户用短信验证码一次操作完成登录，会话按 Bearer token 方向建立。
- 手机号的不同书写形式（裸号/带国家码/含分隔符）归一后指向同一账号；同 Realm 内同一手机号只能绑定一个账号。
- 未注册手机号发起登录不创建账户、不发送验证码，得到未注册提示或注册引导。
- 验证码错误、过期、重复使用、频率受限均按 §4.2 反馈，无法通过穷举或重放绕过；被禁用账号即使验证码正确也被拒绝。
- 自助绑定/换绑/解绑均要求 reauth，换绑与新绑定均需新手机号验证码验证；未配置短信通道的 Realm 不提供绑定入口且直接发起被拒。
- Realm 管理员可配置阿里云/Twilio 通道（凭证脱敏、变更审计、可发测试短信）；未配置时「手机号登录」开关不可开启；关闭后平滑降级且已绑定数据保留。
- 管理员可脱敏查看、按手机号搜索、解绑（二次确认+审计）与换绑（新手机验证码验证后生效）用户手机号。
- 所有配置与处置操作在 Realm 隔离边界内完成，跨 Realm 访问被拒绝。
- 自助注销后该账号手机号经匿名化处理，不能再用于登录。

## 6. 边界与约束

**适用性**: 适用（API 与前端/交互边界合并陈述）

**API / 集成边界:**

- 能力边界：新增短信验证码发送/验证与「手机号登录」能力开关公开状态查询（登录用途，公开端点，状态查询仅返回启用状态）；已认证会话内的手机号绑定/换绑/解绑；Realm Config 体系内的短信通道配置与「手机号登录」开关读写（含测试短信）；管理端用户手机号脱敏展示、搜索、解绑与经验证的换绑；密码登录标识查找扩展为 email/手机号/username 三标识。不新增管理员以外的高权限接口；不改动 email 相关既有端点语义。
- 访问控制原则：公开端点须完成 Client App 级 Turnstile（若启用）与双维度限流；绑定/换绑/解绑要求已认证身份 + reauth 票据，且仅第一方浏览器会话可发起（受限会话与第三方门户会话不持有对应 scope）；通道与开关配置复用 Realm Settings 权限（`settings.view`/`settings.manage`）；用户手机号处置复用用户管理权限（`users.view`/`users.manage`）。
- 租户/realm 数据边界：手机号匹配、唯一性与处置限定在当前 Realm；跨 Realm 数据访问被拒绝。
- 兼容性要求：不修改 `account.email` 的必填语义及其周边链路（软删除匿名化、验证码、OAuth email 匹配）；不触碰 TOTP/MFA；LDAP 用户名登录分支不受三分流影响；未开启开关的 Realm 行为与现状完全一致；纯数字 username 的既有精确匹配路径不受手机号解析影响。

> 端点清单、参数 schema、状态码矩阵、验证码存储与限流数值不在 PRD 承载范围，下沉到技术设计。

**前端 / 交互边界:**

- 页面入口：
  - 登录页：短信验证码登录入口（可见性由 Realm 开关公开状态查询决定，fail-closed——仅明确启用才展示）；密码登录标识输入框接受手机号（判定顺序：email → 手机号 → username，LDAP 分支不受影响）。
  - Security 设置页：手机号绑定/换绑/解绑入口（未配置短信通道或未开启时不展示，或说明原因——对齐"修改邮箱"入口门控口径；开关关闭时保留已绑定手机号只读展示）。
  - 管理后台 Settings：短信通道配置区（服务商选择、凭证、签名名/模板标识、默认国家码、测试短信）与「手机号登录」开关。
  - 管理后台用户管理：手机号脱敏列/详情展示、按手机号搜索、解绑/换绑操作。
- 关键交互：短信验证码登录与邮箱验证码登录复用同一验证码输入交互模式（输入、重发倒计时、错误反馈）；绑定/换绑流程为 reauth → 输入手机号 → 发送验证码 → 验证生效；管理端换绑在验证完成前展示待验证状态。
- 状态反馈：验证码错误/过期/重复使用、发送频率受限、账号禁用、手机号冲突、短信发送失败、通道未配置门控等均按 §4.2 提供可区分的用户可见反馈；手机号一律脱敏展示；手机号格式校验权威归服务端统一错误，前端仅做非空校验。
- 权限可见性：短信配置与开关入口仅对持相应 Settings 权限的管理员可见；用户手机号处置入口按用户管理权限控制。
- 降级：Realm 未开启手机号登录 → 登录页无对应入口，密码登录不接受手机号标识；用户与管理端绑定/处置入口不可用或隐藏。
- i18n：新增文案按现有登录/设置文案体系扩展，支持中英文。

## 7. 已确认决策

> 本节只收录当前有效的决策与未决问题，记取舍、理由、决策人与重开条件；规则正文只在 §4 定义，DEC/Q 编号保持稳定，供代码注释、测试与跨 PRD 引用追溯。

- **DEC-phone-login-001 · 手机号定位**（user）：手机号是与 email 并列的登录标识：可登录、可绑定验证，email 仍为账户必填身份；不做无邮箱的纯手机号账号，手机通道无自动注册（规则正文见 §4.1）。理由：多数 SaaS 惯例；保持 `account.email` 必填及其周边链路（软删除匿名化、验证码表、OAuth email 匹配）不变。落点：§2.1、§2.2、§4.1。重开条件：用户要求纯手机号（无邮箱）注册。
- **DEC-phone-login-002 · 短信服务商范围**（user）：v1 = 阿里云（国内）+ Twilio（国际），统一通道抽象、手写 HTTP 客户端，不引入官方 SDK。理由：国内外租户各覆盖一家；与现有邮件通道手写客户端模式一致，不引入重量级官方 SDK。落点：§2.1、§4.1。重开条件：需要腾讯云等其他服务商时按同抽象扩展。
- **DEC-phone-login-003 · 二次放号信任模型**（user）：与 email OTP 同等信任——验证码即手机占有证明；管理端解绑/换绑为事后处置；不活跃账号二次验证留待后续迭代。理由：与既有 email OTP 信任模型一致，v1 不增加流程分支。落点：§2.2、§4.1、§5。重开条件：出现二次放号入侵案例或合规要求变化。
- **DEC-phone-login-004 · 存储格式**（agent，实现层）：手机号统一以 E.164 规范化后存储（Realm 级默认国家码解析），唯一性建立在规范化形式上（规则正文见 §4.1）。理由：数据库格式反转代价高、影响全部后续阶段；租户内唯一索引的正确性依赖规范化。落点：§4.1、设计/实现层。重开条件：出现无法规范化的号码格式需求。
- **DEC-phone-login-005 · 注册收集形态**（user）：注册流程不收集手机号；手机号由已注册用户在 Security 设置中自助绑定；手机号能力可用性由 Realm「手机号登录」开关控制。理由：降低注册摩擦，email 仍是注册必填身份；手机号作为事后可绑定的并列标识。落点：§2.2、§4.1。重开条件：用户要求注册表单收集手机号或手机号优先注册流程。
- **DEC-phone-login-006 · 开关结构**（user）：单一 Realm 级「手机号登录」开关，同时覆盖手机号作为密码登录标识与短信验证码登录；开启前提为短信通道已配置（fail-closed，规则正文见 §4.1）。理由：手机号占有验证依赖短信通道，无通道时标识本身不可验证；单开关配置面最简，对齐 email_otp「未配置不可开启」门控口径。落点：§2.1、§4.1、§4.2。重开条件：出现「仅标识分流、不开放短信 OTP 登录」的真实租户需求。
- **DEC-phone-login-007 · 管理端换绑验证**（user）：管理端换绑需向新手机发送验证码并验证成功后生效；解绑仅需二次确认并记录审计。理由：维持「已绑定手机号 = 已验证占有」不变式，防止误绑导致短信登录锁死与恶意管理员换绑。落点：§4.1、§5。重开条件：出现管理员无法触达用户手机的特殊处置场景。
- **DEC-phone-login-008 · 首期投放**（user）：不硬性限定首期 Realm；所有 Realm 默认关闭手机号登录，配置短信通道后由管理员自行开启。理由：成本由配置门槛 + 默认关 + 限流/Turnstile 前置控制，无运营侧特殊放开逻辑。落点：§2.2。重开条件：需要收敛投放范围控制短信成本时。
- **DEC-phone-login-009 · 密码登录手机号传输**（agent，实现层）：密码登录中手机号经现有 `login` 请求的 `username` 字段承载（不新增独立请求字段）；服务端在「手机号登录」开关开启时对非 email 的 `username` 输入尝试 E.164 解析并按 email→phone→username 优先级查找，纯数字 username 保留既有精确匹配回退。理由：公开 API/SDK 契约面零破坏——现有客户端与 SDK 无需变更即获得手机号登录能力；反转代价高（公开契约 + SDK + 前端分流 + 测试全链）。落点：§4.1、§6、设计/实现层。重开条件：出现 username 与手机号无法共存解析的输入冲突或需要结构化多标识请求体的真实需求。

> 以上均为已确认并应用的 Active Decision，无 Deferred Questions；决策依据与重开条件见本节各条目。
