## 2. 范围界定

### 2.1 包含功能

- **租户级 LDAP 目录配置**：Realm Admin 为本 Realm 配置企业目录（服务器地址与加密方式、可选私有 CA 证书 PEM（`caCertPem`，与系统信任库叠加用于企业内部 CA 签发的目录证书）、Base DN、服务账号或匿名搜索、用户搜索过滤模板、登录标识/邮箱/显示名的属性映射）并启用/停用。其中登录标识无独立映射配置字段——由哪个目录属性承接登录用户名内嵌在用户搜索过滤模板中表达（如 `(uid={login})`）；仅邮箱与显示名有专属映射字段。
- **登录页企业账号入口**：按 Realm 启用状态显隐的"企业账号登录"表单（企业用户名 + 密码）。
- **目录认证**：后端以标准 search-then-bind 模式完成验证（服务账号检索用户条目 → 用用户凭据向目录验证），兼容 Active Directory 与 OpenLDAP 等标准 LDAPv3 目录。
- **首次登录自动建号与身份链接**：首次认证成功自动创建无本地密码的账号并链接目录身份；用户匹配按 目录身份 → 邮箱 → 创建 逐级进行。
- **完整继承现有登录管线**：人机验证、IP+标识符限流、二因素验证、协议同意、下游授权码分支、会话签发、审计（认证方式标记为企业目录）。
- **公共配置暴露启用状态**：登录页可按租户感知企业账号登录是否启用。

### 2.2 不包含功能 (Out of Scope)

- **LDAP 组 → Herald 角色映射**：目录用户组不自动映射为 Herald 角色/权限（如有需要独立立项）。
- **后台目录同步**：不做账号/属性的批量或增量同步（如有需要独立立项）。
- **Windows 桌面单点登录**：不做 SPNEGO/Kerberos 内网免密自动登录，仅登录页表单认证。
- **SASL 专用机制**：不做 GSSAPI/NTLM 等机制，仅标准用户名密码验证。
- **多目录/故障转移**：v1 每 Realm 单一目录配置。
- **本地凭据缓存或目录离线回退**：目录不可达时企业账号登录即不可用（用户可走其他登录方式）。
- **代理修改目录内密码**：企业密码的修改/重置走企业目录自身渠道，Herald 不写目录。
- **连接池化等性能优化**：如成为瓶颈另行立项评估。
- **目录连接测试端点与主动健康检查**：当前保存配置只做结构与加密信道校验，真实连通性、凭据和 Base DN 在登录使用时验证；管理端没有专用 test-connection 反馈通道。

### 2.3 依赖项

- **本 Realm 既有配置管理能力**：目录配置复用既有租户配置管理（存储、凭据敏感标记与 secrets 读取路径），不新建独立配置体系。
- **现有登录管线**：Client App 上下文解析、人机验证（按 Client App 配置）、IP+标识符限流、TOTP/Passkey 二因素探测、协议同意闸门、下游授权码分支、token 签发（详见 [docs/prd/auth/oauth.md](oauth.md)、[docs/prd/auth/email-otp-login.md](email-otp-login.md) 的既有语义）。
- **既有身份链接与自动建号能力**：第三方登录 JIT 建号范式（无本地密码建号 + 身份链接 + 占位邮箱策略）。
- **协议同意模型**：复用"登录即同意"语义（[docs/prd/core/legal-consent-account-deletion.md](../core/legal-consent-account-deletion.md)）。
- **审计日志能力**：登录事件按认证方式记录（[docs/prd/core/audit.md](../core/audit.md)）。
- **前端登录页状态开关机制**：按 Realm 公共配置显隐登录方式（邮箱验证码/Passkey 入口同型）。

## 4. 业务规则与状态

### 4.1 业务规则

- **租户隔离**：目录配置、用户匹配与账号创建均限定在本 Realm 内；跨 Realm 的配置访问或数据访问被拒绝。
- **每 Realm 单一目录配置（v1）**：配置含启用开关；开关状态作为公共信号供登录页显隐入口。
- **凭据信道加密（硬规则）**：目录连接必须走加密信道（LDAPS 或 StartTLS）；不加密的明文连接配置一律拒绝保存。企业账号密码只允许在加密信道中传输。
- **认证模式**：search-then-bind——以服务账号（或匿名搜索，若目录允许）在 Base DN 下检索唯一用户条目，再用用户提交的凭据完成验证；搜索命中 0 个或多于 1 个条目时认证失败，不做猜测式绑定。
- **注入防护**：用户输入不得直接拼入目录搜索条件；搜索过滤模板仅来自管理员配置并经格式校验。
- **用户匹配策略**：目录身份（用户条目 DN）→ 邮箱 → 创建。目录邮箱由企业管理员在目录中维护，视为可信来源，允许据此登入既有账号；保证同一员工先有本地账号、后接目录时不产生重复账号。
- **JIT 建号授权**：首次目录认证成功即自动建号，**不受 Realm 公开注册开关限制**——管理员启用目录已构成对该目录供给的授权（与既有"自动注册不得绕过注册政策"规则的有意差异，理由见 DEC-support-ldap-007）。LDAP 定位为**凭据权威而非账号唯一来源**：Herald 仍是账号与授权的记录源，不回写、不同步目录（与已排除的目录同步见 §2.2 形成清晰边界）。建号前须满足当前 Realm 生效协议的同意表达（如有）。
- **无本地密码**：目录建号账号没有本地密码，密码登录表单对其不适用；用户后续自行设置本地密码后可恢复密码登录。
- **邮箱缺失容忍**：目录未返回邮箱时以占位邮箱建号（域 `ldap.placeholder`，由目录条目 DN 经 SHA-256 哈希派生——同一 DN 稳定映射同一占位邮箱，不同 base_dn 下的同名登录名不会碰撞）；账户模型无独立 email_verified 载体，建号后直接置 Normal（激活，与邮箱验证码自动建号同形态）。占位邮箱不指向真实邮箱，不得用于邮箱类流程（如密码重置）：该约束为投递层事实行为——占位域无收件方，验证/重置类邮件永不抵达；邮箱类端点没有针对占位域的显式 API 守卫（对占位邮箱发起密码重置/邮箱验证/OTP 等请求可在语法层被受理，仅结果无法送达）。后续登录按目录身份命中，不依赖邮箱。
- **账号状态优先**：目录认证成功但 Herald 账号被禁用时拒绝登录。
- **防枚举**：登录失败返回与既有密码登录一致的泛化错误，不区分"目录里没有这个人"与"密码错误"。
- **防滥用**：继承人机验证（按当前 Client App 的 Turnstile 配置执行）与 IP+标识符限流，不降低既有阈值。
- **管线继承**：二因素验证（TOTP/Passkey）、协议同意（登录即同意）、下游授权码分支、会话签发与审计（认证方式标记为企业目录）全部继承既有登录管线语义。
- **共存原则**：企业账号登录与其他登录方式并列共存、互不影响；停用后平滑降级。

### 4.2 关键状态与异常

- **密码错误 / 目录无此用户** → 泛化"账号或密码错误"，允许重试并受限流约束。
- **目录不可达 / 响应超时** → "登录暂时不可用，请稍后再试"类提示，不暴露目录地址等内部细节；其他登录方式不受影响；故障计入审计与日志供管理员排查。
- **搜索无唯一命中** → 按泛化认证失败处理（含搜索结果多于一条的情况）。
- **目录配置错误**（服务账号凭据失效、Base DN 错误等）→ 企业账号登录不可用，错误通过登录失败和服务端日志暴露；保存时不主动连接目录，当前无管理端连接测试反馈。
- **账号被禁用** → 目录认证成功仍拒绝登录，明确提示账号已被禁用。
- **Realm 未启用 LDAP** → 登录页不展示入口；直接提交企业账号登录请求被拒绝，不创建任何账号或会话。
- **目录邮箱与既有账号一致** → 关联既有账号登录，不重复建号（§4.1 匹配策略）。
- **目录未返回邮箱** → 占位邮箱建号（账户直接置 Normal 激活，无独立 email_verified 载体；占位邮箱不用于邮箱类流程），登录成功。

## 5. 验收目标

- Realm 配置并启用目录后，员工用企业账号一次操作完成登录；首次自动建号，再次登录命中同一账号，不重复建号。
- 先有本地账号（邮箱一致）的员工首次企业账号登录关联到既有账号登录成功，不产生重复账号。
- 公开注册关闭的 Realm，员工首次企业账号登录仍自动建号并可完成登录。
- 目录不可达时登录页给出可理解提示且其他登录方式可用；管理员停用后入口消失，已建账号与其已绑定的其他登录方式不受损。
- 不加密的明文目录地址配置被拒绝保存；服务账号密码在任何配置查看、公共配置与日志中不可见。
- 登录失败不泄露"目录里没有这个人"与"密码错误"的区别。
- 已绑定 TOTP 的用户企业账号登录被要求二因素验证；从第三方应用发起登录时下游授权链路正常完成。
- 审计事件在 `details.method=ldap` 标记认证方式，可在详情中识别；`details.resolution` 记录本次登录的用户匹配级别（`dn_link` 命中目录身份链接 / `directory_email` 按目录邮箱关联既有账号 / `jit_provisioned` 首次登录自动建号，与 §4.1 匹配策略逐级对应）；当前查询 API 不提供按认证方式的独立筛选参数。
- 未启用 LDAP 的 Realm 一切企业账号登录尝试被拒绝且不创建账号。

## 6. 边界与约束

**适用性**: 适用（API 与前端/交互边界合并陈述）

**API / 集成边界:**
- 能力边界：新增一个未认证身份的企业账号认证能力；管理端复用本 Realm 既有配置管理能力（不新增专用管理接口面）；新增独立的公开状态端点暴露企业账号登录启用状态——仅返回 `enabled`，不并入聚合 public-config，不包含任何目录配置细节或凭据（与 email-otp FR-9 同模式）。不新增其他高权限接口。
- 访问控制：企业账号认证为公开端点（无需已认证身份），但必须完成人机验证与限流；目录配置的读写仅限拥有本 Realm 设置管理权限（`settings.view`/`settings.manage`）的管理员。
- 租户/realm 数据边界：认证请求绑定 Realm（与 Client App 上下文一致）；用户匹配与账号创建限定在当前 Realm 内；跨 Realm 配置访问被拒绝。
- 兼容性：与现有密码登录、邮箱验证码登录、第三方 OAuth 登录、TOTP/Passkey、协议同意模型共存；兼容下游 Authorization Code 流程；公共配置新增信号为向后兼容变更。
- 安全约束：服务账号凭据与用户密码不出现在日志、tracing 与公共配置中；用户密码不落存储、不缓存、验证即弃；泛化错误响应防枚举。
- 端点清单、请求/响应参数、状态码矩阵不在 PRD 承载范围，下沉到技术设计。

**前端 / 交互边界:**
- 页面入口：登录页新增"企业账号登录"入口，与密码登录、邮箱验证码等并列；入口可见性由 Realm 启用状态决定；非 Realm 镜像登录页同步支持。
- 关键交互：用户选择"企业账号登录" → 输入企业用户名与密码（完成人机验证，若启用）→ 认证成功后进入既有后续流程（二因素验证/协议同意/完成登录）；首次登录自动建号，无额外注册步骤（Realm 要求协议同意时除外）。
- 状态反馈：认证失败（用户不存在/密码错误）→ 与密码登录一致的泛化错误提示；目录不可用 → "登录暂时不可用，请稍后再试"，并提供其他登录方式回退；账号被禁用 → 明确禁用提示；管理端保存不加密明文目录地址 → 拒绝并提示必须使用加密连接。
- 降级：Realm 未启用 → 入口不展示；管理员停用 → 入口消失，已建账号用户经其他登录方式登录。
- 权限可见性：目录配置入口仅对本 Realm 拥有设置管理权限的管理员可见；服务账号密码回显为掩码或不回显。
- 组件实现形态（与邮箱验证码登录入口同型）由前端设计承接。

## 7. 已确认决策

> 本节只收录当前有效的决策与未决问题，记取舍、理由、决策人与重开条件；规则正文只在 §4 定义，DEC/Q 编号保持稳定，供代码注释、测试与跨 PRD 引用追溯。

- **DEC-support-ldap-001 · 功能范围**（user（未答，agent 按推荐项），2026-08-26）：仅 LDAP 登录认证；不做组→角色映射、不做后台目录同步（各自独立立项）。理由：2026-08-26 AskUserQuestion 范围三问未获用户回答，agent 按推荐项落地（对齐 DEC-wechat-support-012 的未答处理先例）；推荐依据：与现有 WeChat/Apple/Google 外部身份接入深度一致，工作量最小。落点：§2.1、§2.2。重开条件：出现组→角色映射或目录同步的具体客户需求。
- **DEC-support-ldap-002 · JIT 建号**（user（未答，agent 按推荐项），2026-08-26）：首次目录认证成功自动建号：无本地密码 + 目录身份链接；邮箱缺失用占位邮箱（账户直接置 Normal，账户模型无独立 email_verified 载体，规则正文见 §4.1）。理由：同上未答按推荐项；与现有 OAuth JIT 建号模式（`backend/api-oauth/src/helper.rs`）一致，用户零摩擦接入；本地密码列保持 NULL 使本地密码回退登录天然不可能。落点：§4.1。重开条件：租户要求仅管理员预建账号可 LDAP 登录。
- **DEC-support-ldap-003 · 桌面 SSO**（user（未答，agent 按推荐项），2026-08-26）：不做 SPNEGO/Kerberos 桌面单点登录，仅登录页表单认证。理由：同上未答按推荐项；SPNEGO 依赖 GSSAPI C FFI，违背 DEC-wechat-support-004 纯 Rust/no-openssl 硬约束，且浏览器协商流程显著扩大架构与安全面。落点：§2.2。重开条件：出现内网域免密 SSO 的具体客户需求（届时独立立项评估 GSSAPI 之外的方案）。
- **DEC-support-ldap-004 · LDAP 客户端技术选型**（agent，实现层）：引入 `ldap3` 0.12 作为 workspace 依赖：`default-features = false`，`features = ["tls-rustls-ring"]`（不启用 `sync`、不启用 GSSAPI/NTLM），不引入 openssl/native-tls 系依赖。理由：承接 DEC-wechat-support-004（禁 openssl/native-tls 及一切间接拉入 native-tls 的依赖）；ldap3 默认 features 含 `tls`（= native-tls）必须关闭；依赖树已有 rustls 0.23.36 + ring（经 reqwest/tokio-rustls），`tls-rustls-ring` 零新增 TLS 后端；MSRV 1.82 低于锁定工具链 1.96.1。落点：设计/实现层。重开条件：ldap3 出不兼容升级或项目 rustls 主版本迁移。
- **DEC-support-ldap-005 · 配置存储**（agent，实现层）：LDAP 配置存既有 `realm_config`（`config_type='ldap'`，服务账号 bind 密码 `is_secret=true`），复用通用 `/api/configs/{realmId}` 管理 CRUD，不新建独立配置体系；v1 不做应用层加密。理由：对齐 Stripe/Creem/Wechat 凭据存储主导先例（DEC-wechat-support-007 同结论）；不改变技术路线、依赖与兼容性。落点：§2.3、设计/实现层。重开条件：全 provider 凭据统一应用层加密立项（LDAP 一并受益）。
- **DEC-support-ldap-006 · 认证接入形态**（agent，实现层）：新增专用端点（挂 `/api/auth/{realmId}` 下）做 LDAP 登录，完整镜像 `login.rs` 管线（Client App 解析、Turnstile、IP+标识符限流、TOTP/passkey 二因子探测、consent gate、OAuth code 分支、token family、审计 `method="ldap"`）；不在现有 `login.rs` 内部分支。理由：`UserServiceImpl::login` 内嵌 bcrypt 校验与时序均衡逻辑，LDAP bind 无本地哈希可验、无法复用该路径；`email_otp.rs` 已示范"替代第一因子走专用端点"形态，前端按状态开关展示（`EmailOtpLoginForm` 同型）。落点：§4.1、设计/实现层。重开条件：登录页统一单表单交互改版。
- **DEC-support-ldap-007 · JIT 与注册政策**（user，2026-08-26）：自动建号不受 Realm 公开注册开关门控；管理员启用目录即供给授权（与既有"自动注册不得绕过注册政策"规则的有意差异，规则正文见 §4.1）。理由：行业调研（用户要求基于同类产品通行做法）：Keycloak 目录联合登录不受 realm Registration 设置门控、Zitadel 用 per-IdP auto-register（即配置即授权）、Auth0 企业连接首登落库——同类产品均把企业目录视为受控供给而非公开自注册；LDAP 在本 feature 是凭据权威非账号唯一来源（DEC-001 已排除目录同步），"关公开自注册 + 员工目录登录"是企业主场景，注册门控会打断主场景。落点：§4.1。重开条件：出现需要把目录供给与 LDAP 启用解耦细控的客户需求（届时评估 Zitadel 式自动建号子开关）。
- **DEC-support-ldap-008 · 用户匹配策略**（user，2026-08-26）：目录身份（DN）→ 邮箱 → 创建；目录邮箱视为可信（等价已验证）来源，允许据此登入既有账号（规则正文见 §4.1）。理由：镜像 OAuth 四级匹配中可适用层级（`find_or_create_user`：union_id → open_id → email → create，LDAP 无 union_id 概念，DN 即 open_id 载体）；避免员工先有本地账号、后接 LDAP 时 email 撞车导致重复建号或登录失败。落点：§4.1。重开条件：出现目录 email 属性不可信的实际案例（目录属性治理差导致误关联）。
- **DEC-support-ldap-009 · 唯一命中规则**（agent）：用户条目搜索必须唯一命中（0 条或多条均认证失败），不做猜测式绑定（规则正文见 §4.1）。理由：猜测式绑定（取第一条命中）在目录存在重名/多条目时是安全漏洞；唯一命中是 search-then-bind 的行业标准行为（Keycloak 同型），无合理替代方案，属 agent 授权的工程取舍。落点：§4.1、§4.2。重开条件：出现按多值属性（如 uid+org 唯一）消歧的具体目录形态。
